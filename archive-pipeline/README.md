# Бур: изолированная разработка архива

Это тестируемые модули для следующего этапа продукта. Они **не развёрнуты** и не означают готовность универсального сервиса. Production `metzia.store`, опубликованные пилоты и production Supabase не изменялись.

## Проверенная цепочка

`JSON → SHA-256 → закрытый raw object → существующий archive import → SQL-квитанция → чанки → очередь эмбеддингов → поиск → закрытая оболочка`.

Локальный E2E исполняет копию реально прочитанных функций `bur_import_json`, `bur_import_json_safe`, `bur_import_archived_json` в PostgreSQL/PGlite с pgvector. Проверяет сохранение сырого файла, повторный импорт без дубликатов, родителей ответов, подготовку поисковых единиц, подтверждение эмбеддинга и авторизованный API. HTTP Storage/Auth заменены тестовым транспортом; векторы детерминированы. Это проверка корректности цепочки, **не проверка качества живого семантического поиска**.

## Состав

- `verified_import.py`: по умолчанию dry-run; checksum скачанного raw, точная серверная квитанция и отдельное чтение записанных ID перед локальным подтверждением; повторы, атомарная квитанция, без удаления исходников. Известные production URL запрещены.
- `staging-receipt.sql`: серверная проверка записанного пакета по группе, хешу и каждому ID. `SECURITY INVOKER`, только `service_role`.
- `chunks.mjs`: посты и комментарии нарезаются по Unicode-символам с перекрытием; длинные тексты не обрезаются, сохраняются ID родителей и статус неполноты.
- `staging-index.sql`, `index-worker.mjs`: подготовка единиц без дубликатов, временные блокировки очереди, повтор после истечения lease, проверка source_hash при записи. Старые чанки помечаются retired, не удаляются. Старый результат эмбеддинга не принимается как актуальный.
- `staging-search.sql`: членство в группе, закрытый server-only RPC, поиск по словам + pgvector через Reciprocal Rank Fusion, фильтры тем, ссылки и статус извлечения. При отсутствии ключа/провайдера API явно сообщает о поиске только по словам.
- `archive-api/`: проверка Bearer через Supabase Auth `/auth/v1/user`; client-supplied user ID не считается авторизацией. Серверный ключ не передаётся порталу.
- `portal/`: отдельная закрытая HTML-оболочка для тестового размещения; адаптивность, вход/выход, отказ при истёкшей сессии и запрещённой группе, безопасный вывод текста и ссылок. Имена авторов и профили отдельно не выводятся; сам текст ещё требует проверки персональных данных перед публичным размещением.
- `watch_staging.py`: отдельный наблюдатель каталога загрузок. Ждёт стабильного файла, проверяет импорт, по `--index` запускает индексацию. Ошибка не становится подтверждением; исходники не перемещаются и не удаляются. Проверен локально, к облаку не подключён.
- `fixtures/`: структурный снимок и SQL существующего импортёра исключительно для локальных тестов. Нет production-данных и ключей. В тесте `extensions.digest(...,'sha256')` использует встроенный PostgreSQL SHA-256.

## Проверки

```sh
npm ci --ignore-scripts
npm test
python test_verified_import.py
python test_watcher.py
python test_portal.py
```

Python 3.12, Playwright 1.55.0 и установленный Chromium. На Windows для E2E задайте `PYTHON` равным пути к настоящему python.exe. Версии зависимостей зафиксированы в package-lock.json.

## Следующий реальный шаг

Нужен отдельный staging Supabase с копией существующей структуры `archive`/import RPC и закрытым bucket `bur-raw`. Нового облачного проекта в этой работе не создано; доступный список содержит production и неактивный сторонний пилот. Миграции здесь не применены к облаку.

После создания изолированного окружения: применить `staging-receipt.sql`, `staging-search.sql`, `staging-index.sql`; назначить тестовой учётной записи членство `bur_access.group_members`; настроить серверные секреты; развернуть отдельный `archive-api`; в `portal-config.js` указать только staging URL и publishable key. Затем выполнить живой импорт/индексацию/поиск и проверить безопасность. Все изменения production потребуют отдельного явного подтверждения пользователя.

Импорт и индексация требуют явного `--apply --url ...`; ключи передаются только через `BUR_STAGING_SECRET` и `GEMINI_API_KEY`. Не помещать ключи в ZIP расширения, Google Drive или git.

## Оставшиеся ограничения

Наблюдатель Downloads существует отдельно и не настроен на действующий облачный проект; экспорт 0.5.20 не изменён. Полный unattended one-click процесс на живых сервисах ещё не подтверждён. Не проверены production-квоты, реальная скорость/стоимость embeddings, качество поисковых ответов, длительный сбор авторизованной Facebook-ленты, миграция существующих паролей пилотов. Новая оболочка использует Supabase Auth и не подменяет действующие страницы 1543/1643.

Справочные источники: [Supabase Storage access](https://supabase.com/docs/guides/storage/security/access-control), [private downloads](https://supabase.com/docs/reference/python/storage-from-download), [changelog](https://supabase.com/changelog), [PGlite](https://pglite.dev/docs/), [pgvector for PGlite](https://pglite.dev/extensions/).

## Связанные авторы Бура 0.5.24 (только изолированный staging)

`staging-author-graph.sql` — дополнительный контракт после `staging-receipt.sql` и существующих archive importer функций из проверенного schema fixture. Он не установлен в production. JSON с `relational_schema=bur-author-graph/1` направляется Python importer в `bur_import_archived_graph`; локальное подтверждение допускается только после `bur_verify_graph_receipt`. UUID в БД связываются с исходными author_key без отождествления людей по одному имени. Комментарии, родители, исходные ссылки/медиа и точные даты сохраняются. В режиме update существующие посты/обсуждения пропускаются; `update_baseline=true` явно обозначает начальный мост.

Для index-worker оригинальный SHA-256 обязателен: `bur_graph_indexable_posts` разрешает только ID действительно применённых постов, чтобы индексация не обновила старые обсуждения через смешанный raw-пакет. Все новые RPC — SECURITY INVOKER, доступны только service_role. SQL исполняется в локальном PostgreSQL/PGlite в `test-author-graph.mjs` вместе с настоящим Python watcher и локальным HTTP Storage/RPC транспортом. Проверяется потеря квитанции после серверного commit, restart/idempotency, авторы, reply-before-parent, метаданные, new-only delta, пустое пополнение, откат ошибочного пакета, запрет публичных ролей. Сам контракт авторов не тестирует векторы; отдельный существующий E2E исполняет pgvector и индекс.

Эта поставка расширения не запускает установленный watcher и не применяет SQL в какой-либо удалённой БД. Для последующего развёртывания нужен отдельно согласованный тестовый проект и явная установка схемы; это не инструкция менять production.
